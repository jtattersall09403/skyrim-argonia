## Findings first (ranked by usefulness to us)

### 1. Mutagen itself models every record we need, and the models are writable [V]
- Link: https://github.com/Mutagen-Modding/Mutagen, GPL-3.0, 176 stars, supports Skyrim, FO3, FO4, Oblivion, Starfield. Record definitions read from raw XML at `Mutagen.Bethesda.Skyrim/Records/Major Records/`:
  - `Landscape.xml`: `VertexHeightMap` (float `Offset`, 33x33 `Int8` `HeightMap`, 3 bytes unknown), `VertexNormals` and `VertexColors` (33x33 `P3UInt8`), `Layers` (BTXT/ATXT, `AlphaLayerData` for VTXT), `Textures` (VTEX).
  - `NavigationMesh.xml`: `NavigationMeshData` with `NavmeshVersion` (default 12), `CrcHash` (default 0xA5E9A03C), `Vertices` (`P3Float`), `Triangles` (`P3Int16` vertices, three edge-link `Int16`, `Flags`, `CoverFlags`), `EdgeLinks` (to another `NavigationMesh` + triangle index), `DoorTriangles` (to a `PlacedObject`), grid divisor, `Min`/`Max`, `NavmeshGrid` (custom binary). Parent is either `WorldspaceNavmeshParent` (worldspace + `P2Int16` coordinates) or `CellNavmeshParent`.
  - `NavigationMeshInfoMap.xml`: NAVI with `NavMeshVersion`, `MapInfos`, `PreferredPathing`.
  - `Worldspace.xml` (WRLD, with `LandDefaults`, `MapData`, `OffsetData`, `SubCells`), `PlacedObject.xml` (REFR), `Quest.xml`, `DialogTopic.xml`, `DialogResponses.xml`.
- How we use it: ADOPT as the terrain writer and the record layer of the navmesh writer. The terrain writer we planned is a loop over 126x126 cells filling `VertexHeightMap`, normals, colours, layers. The 4033² heightfield at 1.828 m maps one sample to one vertex, so the maths in skyrim-tooling §1 row 67 stands. The UESP LAND page (`Skyrim_Mod:Mod_File_Format/LAND`) [V] gives the encoding to unit-test against: signed bytes times 8 units, first value of each row adjusts the running height carried north, edge vertices must equal the neighbour cell's.
- Unverified: whether the NAVI map-info list needs every navmesh in the worldspace listed with exact grid/centroid data to load in game. UESP's NAVI page [V] does not say it is derived. The Skywind handbook says NAVI "generated by the CK" [V] and tells navmeshers not to edit it in xEdit. tes4skyrim claims to write NAVI itself [V, README], which is the only evidence it can be done outside the CK.
- Replaces: our "terrain writer" (fully), the navmesh converter's serialisation half (fully).

### 2. tes4skyrim (RastaBoy/tes4skyrim, fork of bryantmh/tes4skyrim), the closest existing end-to-end "foreign game data to Skyrim plugin" pipeline [V]
- Link: https://github.com/RastaBoy/tes4skyrim (489 commits, 0 stars) and https://github.com/bryantmh/tes4skyrim (264 commits, 3 stars). Pre-alpha / early alpha, Python 3.14 so 2026. Own code MIT; `external/` has mixed licences (vendored PyNifly code GPL-3.0; two binaries statically link Havok; do not redistribute).
- What it does (README, read): exports TES4 binary to a KEY=VALUE text cache, then `tes5_import/` writes TES5 binary ESM/ESP with all record transforms. Includes:
  - Navmesh "built from scratch: collision is voxelized and triangulated per-cell into Skyrim NAVM/NAVI data using the original Oblivion pathgrid as a guide." Uses scipy (Delaunay), shapely (corridor boolean union), mapbox_earcut (fallback). A compiled native module (CPython 3.14, 64-bit Windows, `native/build.py`) does the heavy part. Authors say it "still needs a lot of refinement, but it mostly works." It also downloads a prebuilt navmesh cache from GitHub releases, which tells us a full-world navmesh is slow.
  - Terrain and object LOD baked once per load order, object LOD via `LODGenx64.exe` (xEdit's LOD generator) in `external/`, terrain LOD composited with Pillow.
  - DIAL/INFO/QUST restructured into DLBR/DLVW/VTYP branch architecture, voice-file renaming, Papyrus transpile (`.psc`), lip-sync via the CK's LipGenerator, `.fuz`.
  - Behaviour graph generation for creatures; Havok MOPP bridge; SpeedTree rebuild.
  - Validated on Oblivion.esm, about 16 GB RAM peak on a 7950X3D.
- How we use it: BORROW METHOD, do not adopt code. (a) Voxelise collision, triangulate per cell, write NAVM/NAVI is exactly the approach the 2.W4 brief plans; its repo is the existence proof and the place to read how it fills edge links, NAVI and cover. (b) It proves LOD can be driven by calling an xEdit-family exe from a script. (c) It is Python and Windows-bound for the native navmesh module; we would rewrite the algorithm in our own language against Mutagen or bethkit. Read `tes5_import/` and `native/` before writing our navmesh converter (GitHub tree pages are robots-blocked to the fetcher; clone to read).
- Replaces: part of the plan for the navmesh converter (reduces design risk, not code).

### 3. universal-modder knowledge note: a Claude Code agent wrote a Skyrim SE plugin with a ~600-line Python writer, tested in game over ~68 builds [V]
- Link: https://github.com/rehan-remade/universal-modder (MIT; fork at SkyrimAIDev/universal-modder), note `knowledge/games/skyrim-special-edition/rebuilding-a-cut-gatekeeper-with-generated-plugin-records-di.md`, dated 2026-10-24, "Claude Code (Opus 5.5)", status working. The knowledge index lists 38+ game notes; the only Skyrim-record one is this. The general Bethesda notes are `techniques/bethesda-plugin-record-format-esm-esp-esl.md` and `bethesda-esl-light-masters-and-plugin-archive-pairing.md`, plus running xEdit under Wine.
- What it generated: an ESL-flagged ESP, Skyrim.esm master only, by cloning vanilla records and writing groups, VMAD, conditions and voice files; dialogue branches (DLBR DNAM flags 0x1 top-level, 0x2 blocking, 0x4 exclusive), shared INFO, force-greet packages, a quest-driven exam. Gotchas are directly reusable: an exclusive+blocking greeting branch (0x6) permanently muted an NPC after one run (gotcha 19); voice path is `sound/voice/<plugin>/<voicetype>/<quest>_<topic>_<formid>_<n>.fuz` with the plugin being the record's origin file and EDID share limited to 25 characters; for ESL, voice file FormID is the low 12 bits.
- How we use it: BORROW the gotchas into our dialogue generator spec before 2.4 (people). ADOPT nothing else; the hand-rolled writer is the thing skyrim-tooling already ranks below Mutagen.
- Reality check on "universal-modder Bethesda field notes": the index shows one Skyrim record-writing note, one Fallout 4 recon, and Wine/xEdit; nothing about worldspaces, LAND or navmesh.

### 4. houseCARL (Avick3110/houseCARL; mirror justty32/houseCARL) [V]
- Link: https://github.com/Avick3110/houseCARL, GPL-3.0-only, 42 stars, 3,680 commits, 50 open issues, 2.0.0, C#/.NET (README says .NET 10, an earlier page capture said .NET 9), Mutagen.Bethesda.Skyrim 0.54.4, Windows x64, Claude Code or Codex. MCP over stdio, 31 tools, 7 skills.
- What it does: reads a whole MO2 load order lazily, writes only to a new plugin by default (verbs Set/Add/Remove/SetAtIndex/InsertAtIndex/ReplaceAll/Merge/CopyFrom), `create` makes records with fresh FormIDs including nested dialogue, `compact_plugin` ESL-compacts, `merge_plugins`, NIF inspect, Papyrus compile/decompile, BSA list/extract/repack, SkyPatcher layer. Schema is generated at build time by reflection over Mutagen (133 record types, 1,174 types, 242 sub-structures). `check` has families: errors (dangling FormLinks, missing masters), scripts, dialogue graph validation (takes seeds, does not sweep), facegen. It does not describe cell, LAND, navmesh or worldspace creation.
- How we use it: BORROW three things. (1) The reflection-driven generated schema is a pattern for our own validation: "record coverage is what Mutagen models, gaps reported by name." (2) The `check` families (dangling FormLinks, missing masters, dialogue-graph) are the checks our generator's output needs; write ours as headless C# using the same Mutagen calls, or run houseCARL as a read-only auditor on a Windows box. (3) Its error-message design ("what went wrong and what to try") suits agent loops. IGNORE as the generator: it is aimed at patching a load order, not building 126x126 cells from JSON.

### 5. DotRecast (ikpil/DotRecast) [V]
- Link: https://github.com/ikpil/DotRecast, zlib licence, 944 stars, on NuGet (DotRecast.Core 2026.3.1 listed [S]), includes `DotRecast.Detour.TileCache` ("navmesh streaming, useful for large levels and open-world games") [V]. Prowl.Recast is another C# port [S].
- How we use it: ADOPT as the polygon generator inside our C# navmesh step if we want it in the same process as Mutagen: Recast voxelises triangles, filters, regions, polygons; then we split to triangles and write `NavigationMeshData`. Recast gives walkable surface and polygons, but not Skyrim's edge flags, cover, door and water triangles, cross-cell links or NAVI; those remain ours (see finding 2 for one worked example).
- Replaces: the Recast half of the navmesh converter (we already bake Recast per `docs/world/72-navigation-ai.md:31` in the old repo, so this is only needed if C#-side).

### 6. bethkit (PyPI) [V]
- Link: https://pypi.org/project/bethkit/, Apache-2.0, v2.5.0, released 2026-10-17, Python 3.10+, Rust core with Python bindings. Reads esp/esm/esl, iterates groups and records, lookup by FormID/EditorID, `PluginWriter` writes new plugins and patches existing ones preserving untouched bytes; BSA and BA2 readers and writers. Typed records come from the Skyrim SE schema only. NIF not mentioned.
- How we use it: CANDIDATE for the Python planning and check side (read Mutagen's output ESM, assert counts, extract BSA contents) with a licence that is easy to bundle. It is eleven days old and one author's schema; do not make it the writer of record. Test it on one LAND/CELL/NAVM round trip against Mutagen output before relying on it. Unverified: its coverage of LAND/NAVM/WRLD.

### 7. Spriggit (Mutagen-Modding/Spriggit) [V]
- Link: https://github.com/Mutagen-Modding/Spriggit, GPL-3.0, 127 stars. Plugin to YAML or JSON, one file per record; CLI `serialize`/`deserialize` is the Linux route (UI is WPF, Windows only); translation logic versioned in NuGet packages (`Spriggit.Yaml.[GameName]`), so old files keep reading after record definitions change. Mutagen.Bethesda.Serialization.Yaml is on NuGet (1.29/1.30 seen [S]).
- How we use it: ADOPT as already planned in 0009. Note: the YAML mirrors Mutagen's record shape, so our Python layer cannot invent fields; generate through a typed C# step, then serialise. A 126x126-cell worldspace will be about 16,000 LAND files plus 16,000 CELL files; check `git` and Spriggit throughput on that count early (not measured by anyone found).

### 8. Skywind and Skyblivion: a negative result worth knowing [V]
- Skywind (https://tesrskywind.com, https://handbook.tesrskywind.com) builds its world space "from scratch at roughly the original game's scale" with newly made assets; its FAQ describes no terrain conversion pipeline [V]. The handbook has sections for navmesh, xEdit guide, Papyrus, 3D, no terrain or converter sections [V]. Navmesh is hand-made by "navmeshers" in the CK, finalised there, reviewed with xEdit (Skywind xEdit guide) [V]. Its public pipeline for Morrowind-to-Skyrim data is not documented. Skyblivion volunteers also navmesh by hand (the project said all Oblivion interiors and a map nearly twice Skyrim's size needed navmeshing) [V]; the Skyblivion repos that are public: Ormin/skyblivion-ScriptConverter (OBScript to AST to Papyrus; PHP/Lua/Mono; 107 commits; licence not shown) and Ormin/skyblivion-NIFConverter (Python+Pascal+PHP; 4 commits; used for Skyblivion and Skywind; no licence shown) [V]. Early Skywind used "complicated tools to convert Oblivion's game data to Skyrim" (Skywind history) [V].
- How we use it: IGNORE as code (no licence, different problem, Windows/PHP). Confirms hand-navmesh does not scale and that no one published a terrain+placement importer. The NIFConverter is relevant only if we ever convert Morrowind meshes (we do not; assets come from Tropical Skyrim and BM&V).

## Surprises
1. tes4skyrim exists and contradicts the 2026-10-27 claim that no public navmesh generator exists. It is pre-alpha, Windows-bound, and keeps a prebuilt navmesh cache because generating is slow.
2. Skywind builds from scratch and hand-navmeshes in the CK; no one published a Morrowind-terrain-to-Skyrim importer, and no GIS/DEM/OSM-to-Bethesda-worldspace project turned up.
3. Mutagen's NVNM has `CrcHash` default 0xA5E9A03C and a custom `NavmeshGrid` binary; the grid byte layout is not in the XML, so writing navmesh through Mutagen needs a read-back test against CK-made data before trust.
4. DynDOLOD's next major version drops its `.pas` scripts [V, sheson]; anything we script against those will change.
5. A named Claude Code session (Opus 5.5) wrote and in-game-tested a Skyrim plugin with ~68 builds in the public universal-modder notes; dialogue exclusivity gotchas cost it half of those builds.

## Recommendations

2. Before scaling any generator, round-trip one vanilla NAVM and one CK-made custom-worldspace NAVM/NAVI through Mutagen read, then write, then in-game path test. Evidence: `NavmeshGrid` is `binary="Custom"`, `CrcHash` has a fixed default, and CK-authored NAVI is the norm (Skywind xEdit guide).
3. Put universal-modder's dialogue gotchas (blocking-only greeting branch, voice path and 25-char EDID rule, ESL low-12-bit voice FormID) into the 2.4 people/dialogue generator spec.
