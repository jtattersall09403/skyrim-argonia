# 0.3: The agent's hands: the bridge, our SKSE build, scenes, the journey runner, the deploy and the timed loop

**Goal.** An agent on the build VM can put the running game into a known state in seconds, act in it, read what
happened, keep a still of it, deploy a new build and get a verdict, with no human. Everything here is reused
before built (decision 0029 §8): the console is the scene tool and a saved game is the studio; the bridge is our
dev-only plugin by SkyLink AI's method, since SkyLink does not load on the pin (§a).

**Starting state (2026-10-29).** 0.2 has installed the Argonia profile on the game machine and its smoke scene
passes; SkyLink AI 175682 is in the profile's dev group, unverified on 1.7.104 (its page lists 1.5.97 and 1.6.x;
MIT by its README; an SKSE plugin plus a .NET 10 MCP server over a named pipe, 74 tools: teleport, time,
weather, console with output, Papyrus calls, quests, inventory, hits and other events, screenshots, save and
load, load order). `infra/gpu-box/run.sh` drives the machine; `infra/stream-client/e2e/drive.mjs` can type into
the real stream (0.0). The reuse audit's SkyLink row and universal-modder's `game-automation` skill are the
prior art.

**Read first.** Decisions 0021, 0022, 0029 (both rewritten), old 0149 (inherited-rulings), [loops.md](../../loops.md);
the SkyLink README and tool list, read from its install; `game-automation` and the field notes on command-file
bridges and unkillable-zombie relaunch (0020 §4).

## Deliverables

### a. The bridge: our dev-only plugin, by SkyLink AI's method
- **SkyLink AI is dropped (2026-10-29, the 0.2 lane):** 1.0.0 (175682, its only file) fails on 1.7.104 with
  "failed to open address library file" (its CommonLib predates Address Library format 5) and raises a modal that
  blocks startup. So `skse/ArgoniaBridge` carries the whole list, with SkyLink's design (a local pipe or socket,
  a token, main-thread tasks, the console with its output) as the method; no re-plan. Route 5, never shipped.
- **One client:** every call an agent makes goes through `tools/bridge.py` (one module, so the transport can
  change under it): a line `<token> <command> [args]` to the plugin's socket `127.0.0.1:47615` on the game
  machine through an SSH tunnel, one JSON line back. The endpoints: `player` (position, heading, health,
  stamina, cell, worldspace, in-air, swimming), `console` (with its output), `save`, `load`, `teleport`,
  `time`, `weather`, the reads (`quest`, `global`, `av`, `inventory`), `events` and `wait_event` (hits, the
  player's animation events, quest stages, menus, each timestamped), `screenshot` and the oracle check (two
  stills differ), `input` (real keyboard presses from inside the game process; the gamepad through `pad.ps1`'s
  virtual pad; capped at 3 s), `frametime`, `nav` (a navmesh path or the failure, between two points), `booth`
  (frame a base record from six angles), and reads of ArgoniaCore values once 1.1 exists. Each endpoint has a
  fail-on-purpose test. Every endpoint is recorded in `docs/research/journals/bridge.md`.
- **Crash handling:** a Crash Logger file or a dead process reports as a failure within 60 s; a relaunch kills a
  zombie first.
- **Cheats are for setup only** (owner, 2026-10-28): god mode, item grants and stage setting may stage a scene;
  the action under test always goes through the real game path. Nothing here ships (0003's release guard
  checks the DLL list).

### b. Our SKSE build, proved
- A CommonLibSSE-NG plugin built **on the game machine with MSVC** (CMake, Ninja, vcpkg; sources rsynced by
  `make deploy`), Address Library for 1.7.104: the first `skse/ArgoniaCore` stub, exporting one native and one
  co-save family with a version (the seam's seed, 1.1 §b), plus `skse/core/` with one pure-C++ unit test run on
  the build VM. The same CMake builds `ArgoniaBridge`.
- **Acceptance:** the DLL loads (SKSE's log), the native answers through the bridge, the family survives a save
  and load, the unit test runs on Linux.

### c. Scenes: a base save and console batch files (decision 0022, rewritten)
- **The base save:** after each deploy, the dev profile starts a new game, runs 0.4's quarantine start, places
  the studio character (one Argonian race, class, birthsign and start kit from 0.4's minimal records) in a
  holding cell, and saves. Scripted through the bridge; never committed.
- **A scene is `tests/scenes/<id>.txt`**, a console batch file (`coc` or `player.moveto`, `set gamehour to`,
  `fw`, items, stages, `player.setav` for the sheet until 1.3's setters exist, `placeatme` for who stands
  where), applied with `bat <id>` from the base save. Every setting goes through what the game itself does. A
  scene never sets what its check tests (loops rule 4). The owner types the same `bat` in the console on the
  stream.
- **The fixtures**, generated by 0.4: the proving ground (walls of each climb class wet and dry, water of each
  depth, a ladder, doors, a duel ring) and the booth (a neutral lit cell); studio-only, unreachable in the game.
- **Targets, measured once and kept:** launch to a scene applied; scene to scene (load the base save, `bat`); the
  numbers are recorded, not budgeted, and the planner reads them when it batches L4 work.

### d. The journey runner (decision 0021, rewritten: state and events, stills as evidence)
- `tests/journeys/<id>.yaml`: a scene to start from; steps, each a short action (an input of at most 3 s, an
  activation, a menu choice through the view's message, a wait of game time, or a teleport); expectations on
  state and events with timeouts.
- `tools/run_journey.py`: applies the scene, plays the steps through `tools/bridge.py`, reads state and events,
  **takes a still at every step** and keeps it in `out/runs/<id>/`, reports per step. A failing step's stills
  go to a `reader` with the step's expectation. Three identical failures stop the run; a crash is a failure.
  No agent pilots by looking; no step is judged by pixels unless its brief names an L5 reason.
- The `scene-author` skill: how to write a scene or journey that can fail (stage what is proved, never set what
  is tested, teleport between steps, keep steps short).
- **Acceptance:** ten smoke scenes apply; the 0.2 smoke scene runs as a journey and passes; a deliberately broken
  journey fails at its step with a readable reason and its still; a forced crash reports within 60 s.

### e. The deploy and the timed loop
- `make deploy`: build the plugin on the game machine, regenerate `Argonia.esm` (0.4), rsync outputs, restart
  the game to the main menu, rebuild the base save, wait for the bridge.
- **The loop, once, unattended:** a `deliver-small` agent, given only a brief, changes one record (an NPC's
  greeting in 0.4's block), runs `make deploy`, applies a scene, reads the greeting through the bridge, and
  reports pass or fail. The cycle time (edit to verdict, machine start included) and its cost are recorded in
  `docs/research/journals/bridge.md`; every later batching decision reads them.

## Acceptance (the gate)
§a's bridge answers every call §d needs; §b loads and round-trips; §c's targets recorded; §d's four checks; §e's
cycle recorded.

## Loops (docs/loops.md)
None: a tooling chunk; each harness is proved on a known-green and a fail-on-purpose case before any lane uses it.

## Risks and fallbacks
- **A CommonLib or Address Library change breaks the bridge on the pin:** the bridge is ours, rebuilt by
  `skse_build.sh` in minutes; `bridge.py`'s callers never see the transport.
- **Real inputs are unreliable through a plugin:** the stream drive (`drive.mjs`) sends them through the real
  input path; slower, but proved in 0.0.
- **Loading the base save is slow on the instance:** one save per scene family (same place and hour).

## Deliberately out of scope
A dev panel or any UI for the studio (the console is the panel); a second runner with no game; any game system.
