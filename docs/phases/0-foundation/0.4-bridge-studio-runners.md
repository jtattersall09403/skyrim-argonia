# 0.4: The bridge, the studio and the two runners

- **ArgoniaBridge** is the in-game oracle agents call.
- **The studio** boots straight into any place, for agents and the owner (decision
  [0022](../../decisions/0022-the-studio-boots-into-any-place.md)).
- **Two runners** play one journey script: the core runner with no game, and the eyeless game runner in Skyrim
  (decision [0021](../../decisions/0021-fast-focused-loops-and-the-ladder.md)).

## Deliverables

### a. ArgoniaBridge, production
- Grow the G1 bridge into `skse/ArgoniaBridge`. It is built only in the dev configuration and never shipped. It
  binds to 127.0.0.1 with a per-boot token, and is reached through an SSH tunnel.
- **Endpoints:**
  - `teleport` (`coc`/`setpos`, place id + marker or coordinates);
  - `time` (set hour, time scale, wait N hours), `weather`;
  - `read`: position, cell, quest stages, globals, actor values, AI package, inventory, the dialogue topic list,
    and any ArgoniaCore value through the 1.1 schema;
  - `nav` (path length or failure between two points for an actor);
  - `input` (keyboard or gamepad events, each with a duration cap of 3 s), `activate` (the activation call an
    input makes);
  - `events`: subscribe with game-clock timestamps to hits (Precision callbacks), animation events, quest
    stages, music type and track, sound descriptors and voice lines;
  - `still` (an in-process backbuffer capture with frame counter and hash, from a named vantage or the current
    camera);
  - `booth` (teleport to the booth cell, place a base record, frame it from six angles: the immersion contact
    sheets);
  - `frametime` (median and 1% lows over N seconds).
- **Harness-internal only:** `console` and `papyrus` exist for the scene applier and spike scripts. The journey
  schema and the panel refuse them, and an agent call outside the scene applier is logged and fails review. This
  keeps 0022 §4 true: nothing reachable from a journey or the panel performs a game action.
- Each endpoint has a fail-on-purpose test.
- **Crash handling:** a Crash Logger file, or a dead process, reports as a failure within 60 s, never as
  "still running". A relaunch that finds a zombie process kills it first (the universal-modder note).

### b. The studio (decision 0022)
- **Scenes.** `tests/scenes/*.yaml` with a schema and an L1 check. A scene sets, at step 0:
  - the place id and marker, or coordinates; the hour and the weather;
  - the studio character's sheet and items (a named start-kit record);
  - quest stages, standing, Owing, who stands where.

  Every setting goes through the setters the game itself calls. A field a scene cannot set yet is a red in the
  scene check, never a silent skip.
- **The studio base save.** After each `make deploy`, the studio starts a new game in the dev profile, completes
  the 0.5 quarantine start, places the studio character (built from real race, class, birthsign and start-kit
  records: until 2.1 makes them whole, 0.5 generates one minimal set of an Argonian race package, a class, a
  birthsign and a start kit) in a holding cell, and saves. The save stays on the box and is never committed.
- **The boot.** `skse/ArgoniaStudio` (dev only) loads the base save at the main menu, then applies the scene
  named in `studio.ini`, or the scene an agent posts to the bridge. A scene change reloads the base save, then
  applies the new scene, so no state leaks between checks.
- **Targets, measured and kept as an L1 timing record:**
  - game launch to first scene: ≤ 90 s;
  - scene to scene: ≤ 20 s;
  - deploy to first scene: ≤ 4 min, including the base-save rebuild.

  A miss is fixed in this chunk, not carried.
- **The panel.** A PrismaUI view on a dev hotkey and a pad chord, marked DEV. It uses a minimal version of the
  design system until 1.2 lands. It holds:
  - **Places:** from the world record, with their markers; search by name.
  - **Map:** click to teleport, over the 2.W4 map image once it exists, a plain grid until then.
  - **Scenes:** every scene with a `owner: true` flag.
  - **Time and weather.**
  - **Free camera.**
  - **Overlays:** navmesh, sockets, encounter zones and danger bands, water bodies, region, cell borders, LOD
    tier, frame time. Each overlay arrives with the chunk that makes its data, and the panel lists it greyed
    until then.
  - **Observe:** a read-only panel of the values `read` can reach.
  - **Report here:** the position, a still and a typed note, appended to `~/argonia-findings/` on the box. The
    planner pulls these privately, and they never go into a public issue.

  The panel calls the bridge's functions in process: one implementation, two front ends.
- **What the panel may not do (0149 carried):** grant items, toggle god mode, start fights, or change any game
  value outside a scene. A pull request that adds such a control is refused by review.
- **The fixtures:**
  - the **proving ground**: adapted from the old `place.fixture.proving-ground` and `-b`, generated through the
    0.5 pipeline. It holds walls of each climb class, wet and dry; water of each depth; a ladder; doors; a lit
    target row; a duel ring. It is studio-only and never reachable in the game.
  - the **booth**: a neutral lit cell.

### c. The two runners
- **The journey format** (`tests/journeys/<id>.yaml`):
  - a scene to start from;
  - steps, each an action (an input of at most 3 s, an `activate`, a menu choice through the view's own message,
    a `wait` of game time, or a `teleport` between steps);
  - expectations on state and events, and timeouts.

  The schema refuses a still, a clip or a reader in a journey (decision 0021 §3).
- **The core runner** (`tools/run_journey.py --core`, L2): plays the same file against our systems' rules with
  a world model (positions, cells, actors, inventories as data) and no game. It is built on the rules host G10
  chose; if that is the old TypeScript, the old headless drives are its starting point.
- **The game runner** (`tools/run_journey.py --game`, L4): applies the scene in the studio (or, in `--cold-boot`
  mode for Part 3, launches the dev profile of the installed stack to the real main menu with the studio boot
  off), plays the steps
  through the bridge, reads state and events, and reports per step. It also enforces:
  - the circuit breaker: three identical failures stop the run;
  - a crash is a failure;
  - artifacts go to `out/runs/<id>/`;
  - steps must be short: a step whose input or walk exceeds its cap fails as a defect in the journey.
- **The `scene-author` skill** (from the old `journey-author`): how to write a scene or journey that can fail;
  stage every block proved below, never set what is tested, move by teleport, keep steps short.

## Acceptance
- Ten smoke scenes pass on the game runner. A deliberately broken one fails with a readable reason. A forced
  crash is reported as a failure within 60 s.
- The studio's three timing targets are met and recorded.
- **The sample journey** passes on both runners: teleport to the G4 place, talk to one G5 NPC, learn a topic, ask
  a second NPC about it, save, load, read the topic. A journey broken at one step fails at that step on both.
- The panel's every control works in an L4 check. The panel offers no game-action control (a reader checks a still
  of each tab against 0022 §4).

## Owner check
In the Part 0 check-in. Open the studio on the phone and the Mac, pick **Places → Claywater Station**, walk in,
press **Report here** once with a note, teleport to the proving ground, change the hour to night and the weather
to rain. Reply in the check-in issue with "works" or what got in the way.

## Risks and fallbacks
- **Loading the base save is slower than the target** on the chosen instance: keep one save per scene family
  (the same place and hour), or apply scenes in place with a reset list (each system's 1.1 reset hook), measured
  against leaks with a before/after state read.
- **PrismaUI cannot be shown before the game loads** (the main menu): the boot runs from the bridge and an ini,
  not the panel.
- **The game runner drifts from real inputs:** at least one journey per chunk uses inputs, not `activate`, for
  each action it tests, so the input path stays proved.

## Deliberately out of scope
Any game system; the real main menu, character creation and opening (Part 3); public release builds, which
exclude both dev DLLs by configuration and by the release guard (3.4).
