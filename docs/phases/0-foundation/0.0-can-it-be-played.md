# 0.0: Can it be played? Skyrim streamed to the phone and the Mac, with touch and the GameSir X2s, and a combat test

**Goal.** Before anything else is built, answer the question everything else depends on. Can the owner play
Skyrim SE in a browser on the Honor Magic V5 and the MacBook Air M2, running on an AWS GPU instance in London?
- **Controls on the phone:** the GameSir X2s (USB-C clip, used folded and unfolded, usually unfolded) and
  on-screen touch, with the whole game playable by touch.
- **Controls on the Mac:** keyboard and mouse.
- **Feel:** is it responsive enough for Dark Souls-style combat? The one combat test, with stock souls-like
  mods, is part of this chunk.

Owner: "If that doesn't work or is too laggy then there's no point doing anything else."

This is gate **G0**. Nothing in 0.1 onwards starts before G0 passes. Agents stop at the owner session and do not
work ahead.

**Starting state.** Setup steps 1–8 are done (`infra/OWNER-SETUP.md`):
- the budget alert, and the build VM (m7i-flex.xlarge spot) with its tunnel signed in with GitHub;
- Claude Code and `gh`, whose token has the `repo` scope, so it can read the owner's private old repo;
- the agent's IAM policy, the GitHub wake role (`AWS_WAKE_ROLE_ARN` repo variable), the idle backstop alarm;
- Skyrim SE and Dark Souls Remastered downloaded on the build VM under `~/games` (Morrowind is not owned on
  Steam, so it is not used);
- `NEXUS_API_KEY` in `~/.argonia/secrets.env`;
- the GPU spot quota at 8 vCPUs.

**Expected agent time:** about 1–2 hours, plus the owner's session. Measure it.

**Re-check before starting:**
- Windows GPU spot prices in eu-west-2: g5.xlarge (default: under 5% interruptions), g6.xlarge, g4dn.xlarge;
- the current Moonlight-Web, Sunshine (or Apollo) and Amazon DCV versions;
- the AWS NVIDIA driver for Windows G instances (the gaming or GRID driver).

**Read first.** Decisions 0007 and 0008; [hosting-streaming](../../research/2026-10-27/hosting-streaming.md);
the owner's 2026-10-28 rulings in [owner-brief.md](../../owner-brief.md); [infra/OWNER-SETUP.md](../../../infra/OWNER-SETUP.md).

## Deliverables

### a. Unattended running, first of all
Spot interruptions happen from day one (the owner was interrupted three times during setup), so this comes first.

- **Smart idle-stop on the build VM:** `infra/build-vm/idle-stop.sh` as a systemd timer. It stops the machine
  after 20 minutes with all three of:
  - no Claude Code activity (no transcript writes, no running tool);
  - no `job_guard` job;
  - no VS Code tunnel client.

  The owner's CloudWatch alarm (an hour under 2% CPU) stays as the backstop.
- **Resume only what was interrupted (owner ruling).** The machine may have been stopped by the idle-stop, a
  spot interruption (the persistent spot request restarts it when capacity returns), the owner or a wake. On
  every boot `infra/build-vm/resume.sh` opens tmux session `argonia` in the repo, running Claude Code in `auto`
  permission mode, and picks one of three modes from the clean-stop marker in `~/.argonia/state/`:
  - **No marker:** the machine stopped mid-task. Claude resumes with `infra/build-vm/prompts/resume.md`: read
    PROGRESS, every `in progress` row and its hand-off note, and new owner comments, then relaunch lanes from
    their hand-off notes and last commits. Subagents cannot be revived, so every lane commits at each green step.
    A GPU-box job interrupted mid-run reruns from its last checkpoint under `job_guard.sh`.
  - **Marker, and an owner comment since it:** woken by a reply. Claude acts on the comments
    (`prompts/wake.md`).
  - **Marker, nothing new:** the owner started the machine. Claude waits at its prompt; nothing resumes and
    nothing stops the machine on the owner.

  An agent that stops on purpose runs `tooling/agent_stop.sh "<why>"`, the idle-stop writes the marker when it
  stops an idle machine, and the `UserPromptSubmit` hook in `.claude/settings.json` clears it when work starts.
- **The owner inbox, done properly.** It replaces the old repo's single running issue.
  - **Two issue forms:** `.github/ISSUE_TEMPLATE/owner-check.yml` (play something, as a checklist) and
    `owner-call.yml` (decide something, with choice fields).
  - **Each issue:** assigned to `jtattersall09403` (GitHub mobile pushes it), labelled, with a milestone per
    part. It is closed with a link to the commit once the answer is recorded.
  - **Status** lives in the repo, not in issues.
  - **`tooling/owner_inbox.py`** creates and reads these. It posts through the `inbox` workflow, so every agent
    issue and comment comes from github-actions[bot] and GitHub notifies the owner (it never notifies anyone of
    their own actions, and the build VM's `gh` is the owner's account).
  - **Issues the owner opens (owner ruling):** they wake the build VM like a comment does. A PostToolUse hook
    (`owner_inbox.py --hook`, at most every 4 minutes) tells a working agent about new owner items. Each one is
    acknowledged at once with how it will be actioned (`--ack`), then answered with what was done and closed
    (`--done`).
- **Wake on reply:** `.github/workflows/wake.yml`.
  - It triggers on `issue_comment` and runs only when the commenter is `jtattersall09403` and the issue carries
    an owner label. The build VM's `gh` is signed in as the owner too, so every agent post carries the marker
    `<!-- argonia-agent -->` and the workflow and `owner_inbox.py` skip marked comments.
  - The wake role's trust policy accepts both GitHub OIDC subject forms (this repo uses the immutable,
    id-based one).
  - It runs in `concurrency: wake` (queued, never parallel) and assumes `vars.AWS_WAKE_ROLE_ARN` through OIDC.
  - It starts the one instance tagged `Name=argonia-build` only if it is stopped, and never creates one.
  - It comments back if AWS has no spot capacity.
  - It takes seconds; nothing long runs in Actions.
- **The stop rule (owner ruling):** an agent stops only when its work is complete, when a critical blocker needs
  the owner, or at a handover the owner asked for. It then opens the owner issue and lets the machine idle-stop.
- **`tools/owner_setup_check.sh`:** confirms each setup item without printing any secret, and ticks
  `infra/OWNER-SETUP.md`.
- **Acceptance:**
  - stop the VM by hand mid-task: it resumes on the next start, losing nothing beyond the last commit;
  - an owner comment on a test owner issue starts the stopped VM within two minutes;
  - a comment from any other account, or on an unlabelled issue, does nothing.

### b. The Windows game machine
The game machine runs Windows (owner ruling), so Skyrim, SKSE, the Creation Kit and the modding tools run natively.

- **`infra/gpu-box/create.sh`** (bash, run on the build VM; `run.sh` then drives the machine over SSH) creates
  `argonia-play`:
  - a Windows Server 2022 persistent spot, stopped on interruption, the first with capacity of g6.xlarge,
    g5.xlarge and g4dn.xlarge (on 2026-10-28 only g4dn.xlarge in eu-west-2a had any; a stopped machine can change
    type later);
  - 150 GiB gp3, in the build VM's VPC and AZ, tagged `project=argonia`;
  - an instance role `argonia-play-ssm`;
  - a security group allowing SSH (OpenSSH server) from the build VM only, plus UDP 40000–40020 for
    Moonlight-Web's WebRTC video (the owner added it; it carries only streams negotiated through the gated page).
- **The sign-in gate (owner ruling):** no web port is open. `cloudflare_gate.py` makes a named Cloudflare
  tunnel from the machine behind Cloudflare Access on the owner's domain: `play.<domain>` (Moonlight-Web) and
  `dcv.<domain>` (DCV) admit only the owner's email (one-time code), sessions 30 days.
- **`infra/gpu-box/setup.ps1`** (stages base, stream, dcv, redist, combat):
  - the AWS GRID driver (public bucket, NVENC, licensed on EC2); the gaming driver needs the machine role's S3
    read, which now exists, and is tried only if frame time asks for it;
  - the desktop pinned to 1920×1080 at every logon (the T4's own head; DCV is told never to resize it or lock the
    session on disconnect, and Windows' idle lock is off, because a locked desktop blocks the stream);
  - Windows Server's gaps for Skyrim: the DirectX June 2010 runtime (XINPUT1_3), Media Foundation, the Xbox 360
    pad driver (Update Catalog) and ViGEmBus 1.17 (an admin extract of its MSI, since every installer refuses
    Server), and `steam_appid.txt` so the game starts without the launcher;
  - Steam, Mod Organizer 2, the streaming hosts (§c), and `idle-stop.ps1`: it shuts down after 15 minutes with no
    stream client and no agent (SSH or `C:\argonia\state\busy`).
- **Owner step (O-7), done 2026-10-28:** the owner signed in to Steam once through DCV. The game files were
  copied from the build VM (Steam accepted them as installed); Steam is offline, and the manifest is pinned
  read-only to build 24914197 (runtime 1.7.104.0). The Creation Kit is left for 0.1.
- **Steam refresh:** `infra/gpu-box/steam_check.ps1` runs at each box start. If Steam refuses an offline launch,
  GPU work stops and an owner call asks for a re-login.
- **Record** the Skyrim depot manifest ids (decision 0002) and the measured per-hour cost in `infra/README.md`.

### c. The stream, three ways, with our own client page
- **Hosts on the game machine:** Sunshine v2026.914 (chosen over a dormant Apollo) and Amazon DCV 2026.0.
  Moonlight-Web runs beside Sunshine on localhost and is paired by `pair_moonlight_web.py` with Sunshine as
  `127.0.0.1`, not `localhost` (Windows resolves that to `::1` and the media sockets then fail).
- **Clients:**
  1. **Moonlight-Web in the browser.** It is GPL, so we fork it as **our client page**, adding the touch layer
     and the metrics.
  2. **The DCV web client in the browser.**
  3. **The Moonlight Android app on the phone** (the owner may install it), as a comparison.
- **The touch layer:** ported from the old repo's on-screen touch controls (read through `gh`), keeping what was
  good. It sends virtual gamepad input, so Skyrim only ever sees a gamepad. It is laid out for the Magic V5
  unfolded first, then folded. **The whole game must be playable by touch**, combat included, even if less well
  than with the X2s.
- **Automatic metrics, never recorded by hand.** Our client page logs every session to the game machine, and
  the agent collects the logs:
  - network type, round trip, jitter, packet loss, bitrate, frame rate, decode time;
  - **press-to-screen latency:** the host draws a small corner marker the moment it receives an input, and the
    page detects it in the decoded frame.

  For DCV and the Android app, the agent records what each exposes.
- **The X2s** is a standard USB gamepad to Chrome on Android. Check every button, both sticks and the triggers
  against Skyrim's XInput layout: no stuck inputs, and rumble if passed through.
- **Readability:** the dialogue text, the HUD and a menu list must be readable on the phone in both shapes.
  Record the UI scale needed.
- **Frame time:** median and 1% lows in the scene, and whether the instance is CPU or GPU bound.

### d. The combat test (the one combat test; owner ruling)
- Through the Nexus API (`NEXUS_API_KEY`, `nexus_fetch.py`), a stock souls-like stack chosen by the same-day
  research (`docs/research/2026-10-28/stream-and-combat-stack.md`), listed by id in
  `infra/gpu-box/combat-test-mods.json`: SKSE, Address Library, SkyUI, MCM Helper, Pandora, OAR, Precision, TDM,
  TrueHUD, TK Dodge RE (its 1.7.99+ addon, on the sprint key, sheathed dodges on) with Dynamic Dodge Animation's
  rolls, step dodges and backstep (owner's pick, 2026-10-29: DMCO's dodge was a forward dash) and IFrame Generator, AMR, SkySA with Elder Souls Sword, OAR-added
  Stamina Cost, Display Tweaks (plus Crash Logger for agents). It is for this test only; nothing is committed or
  shipped.
- **The gamepad in DS1's layout** (owner, 2026-10-29), by button position on the souls-like card:
  - R1/R2 attack (tap light, hold heavy);
  - L1/L2 block, and with R1 a parry (Elden Parry's bash);
  - right button: roll on a tap, run on a hold;
  - bottom: interact; top: jump; left: draw weapon;
  - Start: Skyrim's menu; Back: the journal;
  - d-pad: up favourites, down wait, left/right hotkeys;
  - right stick click: lock-on (TDM); left stick click: sneak; no shout.

  `controlmap.py` makes it on the build VM from the player's own `Skyrim - Interface.bsa` (kept in
  `~/argonia-private`, never committed) to `C:\argonia\controls\controlmap.txt`, and `combat-mode.ps1 on` lays
  it loose in Data. Skyrim did not read `ControlMap_Custom.txt` in My Games. Still not like DS1: a separate
  heavy button, use-item and two-hand.
- **Vanilla or modded by switch, not MO2:** MO2 2.5 would not take a scripted portable instance unattended, so
  `combat_test_stage.py` stages the mods and `combat-mode.ps1` lays them over Data from a recorded list and takes
  them off exactly. The owner's desktop launchers are "Skyrim (vanilla)" and "Skyrim (souls-like mods)".
  Pandora's behaviour output is part of the overlay.
- **Skyrim's path limit:** the loose-file scan overruns a fixed buffer on any path of 260+ characters under Data
  (`0xC0000409` at start-up, vanilla included). Staging drops OAR's "put your … file here" placeholders and
  refuses any longer path.
- **The scene, reached quickly, not through the new game:** saves `ArgoniaRiverwood` (gear given) and
  `ArgoniaBanditCamp` (inside Embershard Mine, `EmbershardMine01`), made through the real stream by
  `infra/stream-client/e2e/drive.mjs` typing console commands (`coc` from the main menu's console skips the
  opening; answer No to the Survival prompt). Cheats are fine for setup.

  - §b: the machine, Steam, and vanilla and modded Skyrim reaching the world;
  - §c: Moonlight-Web over WebRTC through our page, its live check passing inside AWS (keyboard 37.9 ms and
    touch 49.8 ms press-to-screen medians), and DCV behind the gate;
  - §d: the stack, the switch and both saves.
- **Frame time:** at Riverwood (vanilla, g4dn.xlarge), 60.4 fps median (vsync), 50.6 fps 1% low; GPU busy 6.8 ms.
- **Not yet measured:** anything from the owner's own devices and networks. The client page logs it

- **Not set up:** the Moonlight Android app (setup 3). It needs Sunshine's ports opened publicly and a PIN
  pairing, so it is done only if the owner asks in the play-session issue.
- **The owner's first feel notes (2026-10-29, Mac, Moonlight-Web, souls-like stack):** "definitely playable on
  desktop" and combat "felt reasonably good". Not souls-like yet:
  - stagger, poise and animation interrupts;
  - a proper riposte animation (Rim Parry's execution may be it, not yet confirmed);
  - stamina and damage tuning;
  - backstab untested;
  - no kicks, running attacks, roll-attacks or backstep-attacks.

  These are the first rows of 1.4's combat gap register (decision 0019: existing mods, tuned; we build only where
  they fall short), with the owner's single-press backstab; they are not fixed in the 0.0 test stack. Measured on that session: press-to-screen 39.6 ms median for keys (p95 53.4), 53.7 ms
  for the mouse, round trip 5 ms, 60 fps, decode 5.1 ms, no loss, 1844x930 at about 5.5 Mbps (since doubled).
- **Owner check-in open:** #10, the play session round 2 (open the page to start; three setups; parry, riposte and backstab). On the reply:
  1. start the machine (`infra/gpu-box/run.sh start`) if it is stopped;
  2. after the session, collect the metrics and post the per-setup numbers;
  3. record the verdict in decision 0007 and `infra/README.md`;
  4. close the issue.
- **The play switch (owner calls #6, #8):** opening `play.<domain>` (or `dcv.`) is all it takes.
  - The Worker `infra/cloudflare/play-switch.js` sits behind the gate. When the tunnel is down, it starts the
    machine through the restricted IAM user `argonia-play-switch` and serves a page that reloads every 4 s.
  - Measured 2026-10-28: EC2 running at 7 s, tunnel healthy at 19 s, Moonlight-Web listening by about 30 s.
  - Reopening within a few minutes of a stop waits for AWS to finish stopping the spot machine (several minutes).
  - Comments of just **play**/**stop** on an owner issue still work through the wake workflow.
- **Auto-stop, four independent layers:**
  1. `idle-stop.ps1` on the machine: 15 minutes with no client; proved live 2026-10-28, stopped 14 minutes after
     the last SSH; idle time never counts from before the latest boot;
  2. the AWS alarm `argonia-play-no-stream` (`alarm.sh`): under 20 MB out per 5 minutes for 30 minutes;
  3. the Worker's 30-minute schedule: stops it after 8 hours on;
  4. a nightly stop at 03:00 UTC.

  The Worker's `workers.dev` address is disabled, so nothing bypasses the gate.
- **Upstream bug:** a finished or failed WebRTC session can jam Moonlight-Web's UDP socket. `e2e/drive.sh`
  restarts it before each drive; if the owner's stream won't start, restart task `argonia-moonlight-web`.

## The owner's play session (about 45–60 minutes)
One owner-check issue lists, one per bullet:
1. Log in to Steam in the stream (about 3 minutes).
2. **Vanilla:** walk near Riverwood, talk to someone, open the inventory, fight a bandit.
3. **Each stream setup:** Moonlight-Web, then DCV, then the Moonlight app. Use the phone unfolded and folded, on
   Wi-Fi then 5G, with the X2s and then touch only. Then use the Mac with keyboard and mouse.
4. **The souls-like mods at the bandit camp:** roll through swings, block, try parries, lock on, fight two or
   three.
5. **Reply in the issue:** which setup and controls you'd use, whether it is "playable", how combat feels next to
   Dark Souls Remastered (could feel like DS / too laggy for parries / Skyrim's combat is the problem), and
   anything that jarred.

The measured latency for each setup is in the issue by the time the owner replies.

## Acceptance (G0)
- The owner calls at least one setup "playable" with the X2s, and touch workable for the whole game.
- Latency and stream health are logged automatically per setup, device and network.
- Frame time: ≥ 60 fps median and ≥ 45 fps 1% lows on the chosen instance.
- The combat verdict is recorded. It decides whether G6 (measuring DS1) and G9 (timing and our own animations)
  run in 0.2.
- Decision 0007 and `infra/README.md` carry the numbers and the chosen stream setup.

## If it fails
The agent works through these itself, each measured before the next, and asks the owner to try again:
1. The other stream setups, UDP or WebRTC modes, codecs (H.264, H.265, AV1), 900p, a higher bitrate.
2. Another instance type, if frame time is the problem.

If the owner still calls it unplayable, **stop and re-plan with the owner** (an owner call).
