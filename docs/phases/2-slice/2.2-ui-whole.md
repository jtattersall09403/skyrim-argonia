# 2.2: The UI whole: every later screen on 1.12's design system

**Goal.** As each Part 2 system lands, its screens join the one Argonian design system that 1.12 built: Wind UI's
windows under our patch, and our own views where Wind UI stops. The UI map stays complete, every transition is
judged in motion, and **in normal play the player never sees a vanilla Skyrim screen** (soul contract C10, C11;
decision 0017).

**Starting state.** Written by the agent that closes Part 1. Expected:
- 1.12 is done: Wind UI under our patch, the chart, the journal book, the dialogue window, the System pane and the
  HUD's minimap in game on every device;
- the tokens and the UI map are in `ui/DESIGN.md`.

**Re-check before starting:** the Wind UI and PrismaUI versions pinned in the sourcing register.

**Read first.** Decision 0017 in full; 1.12's brief and report; `ui/DESIGN.md`; `docs/research/2026-10-31/windui.md`;
0014 §7–8.

## Deliverables

### a. The UI map kept whole
- Every screen, overlay, popup, notification and prompt the game has is in `ui/DESIGN.md`'s UI map, with who draws it
  (Wind UI under our patch, our view, or the engine's restyled) and every transition between them. The transitions
  include gameplay ↔ dialogue ↔ barter, ↔ the windows, rest ↔ the sitting, death → wake, sleep and wait, loading, and
  chargen → first control.
- Each vanilla surface is listed with how it is replaced, suppressed or restyled: message boxes, "you cannot sleep
  now", the quest-updated and discovery notices, tutorial popups, activation prompts, the tween and favourites menus,
  and the console only in dev builds.
- **Acceptance:** no surface without an owner and no transition without a planned check.

### b. Each system's screens, as it lands
The chunk that builds a system wires its screens. This chunk owns the design system, reviews each wiring and keeps the
screens one language.

| Screen | Drawn by | With |
|---|---|---|
| Magic: spells by school, powers, active effects | Wind UI | 2.9 |
| Spellmaking, enchanting services, training, travel, repair | ours, in the frame style | 2.6, 2.9 |
| Alchemy, smithing and the other stations | Wind UI | 2.10 |
| Crime (the Owing), lockpicking, pickpocketing | ours or the engine's restyled; pickpocketing in Wind UI | 2.11 |
| Factions and bounties | Wind UI's stats pane, under our sheet | 2.4 |
| Barter at our one price, gifts | Wind UI, over our price hook | 2.6, 2.5 |
| Persuasion | ours, in the dialogue window | 2.5 |
| The journal's Topics ribbon, the chart for the slice | ours, in Wind UI's windows | 2.12 |

Where a Wind UI window shows a number or rule we own (a price, a skill, a cost), our rule decides it and the window
shows it; where it cannot, our patch fills it.

### c. Eyes on transitions, in focused loops
- **One UI lane, transition by transition:** one lane owns the design system (no swarm) and works through the UI map
  one transition at a time.
- **A clip for each:** a short in-game clip (**L5, reason: motion and hand-off cannot be judged from stills**), judged
  by readers on five things: no vanilla flash, no jump in style, no focus lost, no input eaten, consistent timing and
  sound. Fix, then re-record, until clean.
- **Who owns which transition:** each system's lane owns its own transitions and judges them on these rules. This lane
  owns the components every transition uses. 2.17 re-measures the whole map once as a survey.

## Acceptance
- The UI map has no surface without an owner and no transition without a planned check.
- Each wired screen passes L3 stills at the four viewports, read as one design, and an L4 open and close by pad,
  keyboard and touch.
- Every transition built so far has a passing L5 judgement.
- No vanilla menu that Wind UI or our views replace can be opened.

## Loops (docs/loops.md)
- **Subsets:** each screen (L3, L4); the map (L1: every router entry has a map row).
- **Joins owned:** every UI-map transition (L5, reason above).
- **Journeys:** none; screens are steps in every system's journey.
